# Easy-Tools 开发、打包与发布规范

本文面向 Easy-Tools 开发者和发布者，记录当前仓库实际使用的约定。涉及用户界面和数据的变更，应同时遵守 [`privacy-design.md`](privacy-design.md)；功能验收以对应的 `_doc/prd/` 文档为准。

## 1. 项目约定

### 代码组织

- `easy_tools/core/` 放业务逻辑、数据处理和系统能力；可独立于 Qt 的逻辑优先保持无 Qt 依赖，便于单元测试。
- `easy_tools/ui/` 放 PySide6 界面和交互。界面线程只做轻量工作；OCR、网络、模型推理、文件扫描和较长流程应放入后台任务，并通过信号回传结果。
- `easy_tools/config/` 放配置结构和默认值；用户运行数据放在 Easy-Tools 用户数据目录，不写回打包资源目录。
- `easy_tools/win32/` 封装 Windows API 声明和调用。新增 API 声明时同时检查位数、参数类型、返回类型和失败处理。
- `installer/` 放安装器、卸载器和更新助手；`tests/` 放回归测试；`docs/` 放面向开发者或用户的长期文档。

### 改动要求

- 优先复用现有动作、配置和服务层接口；配置格式变化应提供兼容迁移，不能静默丢弃用户设置。
- 所有可能阻塞的流程都要考虑超时、取消、异常回传和资源释放；不要在 UI 线程执行网络访问或模型推理。
- 不吞异常、不把失败伪装成成功；给用户的错误信息应能指出下一步，日志保留必要诊断信息。
- 不提交生成物、个人数据、密钥、发布令牌、私有证书、模型权重或运行日志。大模型文件依照 `models/MODEL-NOTICE.txt` 获取并核对许可。
- Python 脚本节点以当前 Windows 账户权限执行，不是安全沙箱。隐私、OCR、云端 AI 和外部工具的变更必须遵守 [`privacy-design.md`](privacy-design.md)，并补充对应回归检查。

### 验证约定

在 Windows 开发环境中，先运行与变更相关的测试；发布前运行完整测试集：

```powershell
python -m pytest -q
```

涉及 GUI 时，还要实际打开对应页面；涉及截图/OCR/隐私时，检查框选、内部 OCR 和窗口捕获排除；涉及输入钩子或安装更新时，检查取消、退出清理和用户数据保留。单元测试通过不能替代打包产物验证。

## 2. 版本和发布内容

发布版本号必须同步更新：

1. `pyproject.toml` 的项目版本。
2. `easy_tools/__init__.py` 的 `__version__`。
3. `installer/installer_app.py` 的 `VERSION`。
4. Git 标签使用 `v<版本号>`，例如程序版本 `0.4.0` 对应标签 `v0.4.0`。

Easy-Tools 有两类发布渠道：

| 渠道 | 用途 | 发布内容 |
| --- | --- | --- |
| GitHub Releases | 用户下载 Windows 安装包、查看版本说明和源码标签 | 极速版 `Easy-Tools-Setup-<版本号>-Lite.exe` 与完整版 `Easy-Tools-Setup-<版本号>-Full.exe`，各附 SHA-256 |
| DownloadCenter 灰度更新 | 已安装客户端接收目录版程序文件的灰度/增量更新 | 完整 `Easy-Tools` 目录，不是安装器 exe |

DownloadCenter 有公司节点 `https://192.168.99.206:9443` 和公网节点 `https://www.clblog.online:9443`。Easy-Tools 客户端优先访问公司节点；网络失败或服务端错误时回退公网节点。发布同一版本时，应将同一个目录版产物发布到两端，应用、平台、通道、版本和灰度比例保持一致。

## 3. Windows 打包

### 环境准备

使用 Windows x64 环境，并确保可使用 .NET Framework C# 编译器 `csc.exe`。0.4.1 使用 Python 3.12；建议独立虚拟环境，安装经过本版验证的构建依赖和测试工具：`python -m pip install -r requirements-build.txt pytest`。不要直接升级 ONNX Runtime、NumPy、OpenCV 后沿用旧的原生验证结论。目录版打包还需要：

- 完整版包含 `models/SmolLM2-360M-Instruct-Q4_K_M.gguf`（不纳入 Git，按 `models/MODEL-NOTICE.txt` 下载）；
- `vendor/llama/llama-server.exe` 及配套 DLL。

OCR 后端通过 PyInstaller 收集；如果依赖缺失，构建会失败。发布前确认模型来源及许可证文件在包内。

极速版通过显式 edition 构建，不携带 GGUF 权重；完整版仍内置权重。极速版首次需要模型时，用户可在“综合配置 → 本机模型”主动下载固定 Hugging Face revision，下载过程显示进度、允许取消并校验 SHA-256；模型只写入 `%APPDATA%/Easy-Tools/models`，不会上传用户内容。该路径独立于程序安装目录，覆盖安装和应用内更新不会清理它；后续版本会自动发现并复用已校验的模型文件，不会重复下载。隔离输出示例：

```powershell
python build.py --edition lite --tag 0.4.1-lite --no-smoke
python build_installer.py --edition lite --tag 0.4.1-lite --no-smoke
python build.py --edition full --tag 0.4.1-full --no-smoke
python build_installer.py --edition full --tag 0.4.1-full --no-smoke
```

### 构建步骤

先同步版本号，再分别构建极速版和完整版，用标签隔离目录，避免覆盖现有 `dist/`：

```powershell
$version = '0.4.1'
python build.py --edition lite --tag "$version-lite" --no-smoke
python build_installer.py --edition lite --tag "$version-lite" --no-smoke
python build.py --edition full --tag "$version-full" --no-smoke
python build_installer.py --edition full --tag "$version-full" --no-smoke
```

产物位置：

- 极速版目录：`dist-<版本号>-lite/Easy-Tools/`
- 完整版目录：`dist-<版本号>-full/Easy-Tools/`
- GitHub 安装器：`Easy-Tools-Setup-<版本号>-Lite.exe` 和 `Easy-Tools-Setup-<版本号>-Full.exe`

`build.py --tag` 配合 `--no-smoke` 只构建目录版，不代表产物验证完成。当前 `smoke_exe.py` 固定测试 `dist/Easy-Tools`，并会结束所有名为 `Easy-Tools.exe` 的进程、删除 `%APPDATA%\Easy-Tools`；不要在日常用户配置或有运行实例的电脑上直接运行。要执行该完整冒烟关卡，请使用一次性 Windows 测试账户/虚拟机，并先确认其中没有需要保留的 Easy-Tools 用户数据。安装器构建默认会检查模块并运行 `--selftest`，只验证安装包载荷，不会执行安装。

### 产物检查

发布前至少完成以下检查：

1. `python -m pytest -q` 全部通过。
2. 安装器命令退出码为 0，载荷自检输出 `ok=True`。
3. 在干净的 Windows 测试环境安装或覆盖安装；确认启动、托盘、中键面板、配置中心可用，卸载/覆盖升级保留用户配置。
4. 核对版本号、安装包图标、文件大小和 SHA-256；确认不是旧版本残留。
5. 涉及隐私、截图、OCR、输入法、事件链或更新功能时，执行对应的专项回归并记录结果。

生成安装包校验值：

```powershell
Get-FileHash ".\dist-installer-$version-lite\Easy-Tools-Setup-$version-Lite.exe" -Algorithm SHA256
Get-FileHash ".\dist-installer-$version-full\Easy-Tools-Setup-$version-Full.exe" -Algorithm SHA256
```

不要把未通过验证的 `--no-smoke` 构建描述为已完成产物验证。安装器通过载荷自检也不等同于在目标 Windows 环境完成安装/覆盖升级验证。

`--selftest-upgrade --native --output <诊断目录>` 使用合成内容检查新增窗口的捕获排除、办公处理及后台 UI 心跳。`--selftest-capture --report <报告路径>` 执行原生 GDI 与真实 OCR 专项。应在隔离 APPDATA 或测试账户执行，不替代真实 Office、录屏软件和低配长稳验收。每次发版记录已验证范围和缺口，详见 [0.4.1 验证记录](releases/0.4.1-validation.md)。

## 4. 发布到 GitHub Releases

1. 确认 `main` 上的发布提交已通过评审和验证；提交信息简洁说明改动。推送前检查：

   ```powershell
   git status --short
   git diff --check
   git push origin main
   ```

2. 为同步后的版本创建并推送标签（每个版本标签唯一）：

   ```powershell
   git tag v$version
   git push origin v$version
   ```

3. 在 GitHub 项目页打开 **Releases → Draft a new release**，选择标签 `v<版本号>`，填写面向用户的变更说明。
4. 上传极速版 `Easy-Tools-Setup-<版本号>-Lite.exe` 和完整版 `Easy-Tools-Setup-<版本号>-Full.exe`；在说明中分别附上 SHA-256。不要上传构建缓存、用户配置、令牌、证书私钥或单独的 `.gguf` 模型权重。
5. 检查附件名、版本标签、说明和校验值一致后发布 Release。发布后从 GitHub 下载一次附件，重新计算 SHA-256 并比对。

GitHub Release 用于安装器分发；不要把 `dist/`、`build/`、测试数据或包含个人数据的压缩包当作发布资产。

## 5. 发布到 DownloadCenter

### 发布前

- 确认安装包已验证，目录版来自同一版本、同一构建。
- 每个 `app/platform/channel` 下版本号必须唯一且高于当前版本；已发布版本不可覆盖。灰度放量要发布新的、更高版本，不要尝试修改旧版本。
- 生产发布使用 `app=easy-tools`、`platform=windows-x64`、`channel=stable`。灰度比例取 `0–100`；通常先小范围（例如 10%），观察稳定后以新版本逐步扩大，最终到 100%。设置 0% 可暂停该候选版本的下载。
- 令牌从更新中心管理员处安全获取，仅放在当前 PowerShell 进程环境变量中；不要写入脚本、命令历史、仓库或文档。

### 网页方式

1. 打开公司更新中心 `https://192.168.99.206:9443/`。首次使用时按 DownloadCenter 项目说明导入公司 CA 到当前 Windows 用户的受信任根证书，并重启浏览器；不要关闭证书校验。
2. 连接发布权限，输入管理员提供的发布令牌。
3. 选择本次构建目录 `dist-<版本号>/Easy-Tools/`，填写应用标识 `easy-tools`、版本号、`windows-x64`、`stable`、灰度比例和简短版本说明。
4. 发布成功后在版本记录中核对版本、目录文件数、大小、通道和灰度比例；在 Easy-Tools 配置中心检查更新，使用灰度测试实例确认候选版本可见、下载并校验。
5. 对公网节点重复发布同一个目录版，地址为 `https://www.clblog.online:9443/`。公网节点必须使用有效 HTTPS 证书；公司和公网两端的元数据字段、版本和灰度比例必须一致。

### 命令行方式

推荐用仓库脚本对两个独立节点发布同一版本，并在两端核验版本、文件数、总大小及三版本历史后清理本地发布归档。需要先在两个节点部署支持 DC-001-AC12 的 DownloadCenter 服务；脚本不关闭 TLS 校验，令牌仅从当前进程环境读取：

```powershell
 $env:DOWNLOADCENTER_TOKEN = '<安全获取的发布令牌>'
python scripts/publish_downloadcenter.py 0.4.1 .\dist-0.4.1\Easy-Tools `
  --rollout-percent 10 --notes '版本更新说明'
```

命令会显式发布到公司 `192.168.99.206:9443` 和腾讯云 `www.clblog.online:9443`，同版本部分成功后可重试：已有清单完全一致时会核验并跳过，不一致时停止。服务器每个 `app/platform/channel` 保留三个版本且回收全局不再引用的块。本地只清理脚本管理的 `release-artifacts/`，其中保存最新三个已发布目录和对应块缓存；原始构建目录不被自动删除。完成后清除当前会话中的令牌：

```powershell
Remove-Item Env:DOWNLOADCENTER_TOKEN -ErrorAction SilentlyContinue
```

公司节点 CA 使用 DownloadCenter 仓库 `deploy/server.crt`；公网节点使用操作系统信任的证书链。不要把发布令牌写入 `--server`、`--ca`、命令参数或发布产物。

### 回滚与故障处理

- 发现问题时先把该版本灰度比例设为 0（更新中心的版本不可变，因此需要按平台当前支持的方式发布一个更高版本并设为 0，或由管理员暂停候选版本）；不要删除用户数据或手工覆盖客户端文件。
- 修复后提高补丁版本号，重新构建、验证，并以新版本重新发布到两端。先小比例验证，再逐级扩大。
- 一端发布失败时，不要让两端分别指向不同版本或灰度比例；先修复后补发缺失的一端，再开放更大灰度。
- 发布令牌或私钥疑似泄露时立即联系更新中心管理员轮换；不得将其复制到 issue、截图或日志。
